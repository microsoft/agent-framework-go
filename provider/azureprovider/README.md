# Azure AI Search

Azure AI Search indexes back typed and dynamic VectorData collections, including
the [chat-history memory provider](../../agent/memory/).

```go
search, err := azureprovider.NewAISearch(endpoint, azureprovider.AISearchConfig{
    Credential:         credential,
    EmbeddingGenerator: embedding.Bind(generator),
})
if err != nil {
    return err
}

collection, err := vectordata.GetCollection[uuid.UUID, *Document](
    search.Store, "documents", nil)
if err != nil {
    return err
}
if err := collection.EnsureExists(ctx); err != nil {
    return err
}
```

Here `endpoint` is `https://<service>.search.windows.net`, `credential` is an
`azcore.TokenCredential`, and `generator` produces float32 embeddings. Set
`AISearchConfig.APIKey` to `azcore.NewKeyCredential(key)` instead of `Credential`
for API-key authentication. Azure Identity access to documents requires an
appropriate data role; index creation also requires permission to manage indexes.

```go
type Document struct {
    ID      uuid.UUID `vectordata:"key,storage=id"`
    Text    string    `vectordata:"data,indexed,fulltext,storage=text"`
    Content string    `vectordata:"vector,dimensions=3072,storage=vector"`
}
```

The example schema matches the default dimensions of `text-embedding-3-large`.
An upsert stores `Text` as text and generates `Content`'s vector. Generators run
once per vector property for each batch; property and definition settings override
the store default. Native float32 vectors need no generation.

- Use `search.DynamicCollection(name, definition)` for `map[string]any` records.
  On Go 1.27, `search.Collection[K, R](name, definition)` is also available.
- UUID keys are generated by default. Use pointer or map records to observe them
  on the input; disable generation through the key definition when needed.
- Storage names come from VectorData definitions and tags, not record `json` tags.
  Only schema properties are uploaded. Go `int` maps to `Edm.Int64`.
- Nil collection fields, including native vectors, are uploaded as empty arrays
  without changing input records. Nullable scalar fields remain null.
- HNSW and cosine similarity are defaults; flat indexes, dot product, and
  Euclidean distance are also supported.
- String queries without a generator use Azure AI Search vectorization. This
  requires an existing index with a configured vectorizer; the connector does not
  provision vectorizers.
- Vector fields are excluded from retrieval by default. Generated fields cannot
  be retrieved with `IncludeVectors`. Hybrid search supports full-text data fields.
  Score thresholds filter service-ranked candidates on the client.
- Batch writes can partially succeed. All per-document failures are returned;
  generated input keys are not rolled back. Stores and collections do not close
  borrowed credentials, generators, or transports.

The connector uses the Azure `azcore` pipeline with REST API `2025-09-01`.
Behavior follows the
[pinned .NET connector](https://github.com/CommunityToolkit/AI/tree/7a48d308df63d85427a772f031616889905a0fdf/MEVD/src/AzureAISearch).

See the [runnable example](../../examples/02-agents/providers/azure/ai_search/).

## Live validation

The integration tests create uniquely named indexes and delete only those indexes.
They require permission to manage indexes and documents.

```powershell
$env:RUN_AZURE_AI_SEARCH_INTEGRATION_TESTS = "true"
$env:AZURE_SUBSCRIPTION_ID = "<subscription ID>"
$env:AZURE_AI_SEARCH_ENDPOINT = "https://<service>.search.windows.net"
go test -count=1 .\provider\azureprovider -run "^TestE2E_AISearch"
```

Set `AZURE_AI_SEARCH_API_KEY` to test key authentication instead of Entra ID.
Generated-vector and chat-history memory tests additionally use
`FOUNDRY_PROJECT_ENDPOINT` and a `FOUNDRY_EMBEDDING_MODEL` deployment producing
3072-dimensional vectors (default `text-embedding-3-large`).
